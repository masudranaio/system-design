## Problem framing

The [HLD lesson](/case-studies/ticketmaster/hld) solved double-booking at
the system level: a Redis TTL lock plus a distributed queue keep 100,000
simultaneous buyers from colliding on inventory. This lesson solves the
same problem one layer down — at the object and schema level. If `Seat`
is a class with a plain `status: string` field and a `BookingService`
method that directly sets `seat.status = "booked"` after a bare string
comparison, every code path that touches a seat is a place a race
condition or a forgotten branch can double-sell it. The goal here is to
model seats, holds, and bookings so an invalid transition — confirming a
seat nobody holds, holding a seat that's already held — is either
impossible to express in the type system or rejected by a single
enforcement point, rather than something every caller has to remember to
check.

{/* concept-dependency: LLD-01 not yet built, explained inline */}
Two ideas from object-oriented design do the load-bearing work: **class
relationships** (which object owns which — a `Show` owns its `Seat`
inventory, a `Booking` owns its `BookingItem`s) and **encapsulation**
(a `Seat`'s status only ever changes through its own methods, never by a
caller reaching in and setting a field directly). Neither is exotic; the
Ticketmaster problem is a good vehicle for them because getting the
ownership and encapsulation wrong is exactly how double-booking bugs get
written.

<QuizItem
  question="Why model this at the class/schema level at all, if the HLD lesson already solved double-booking with a distributed lock?"
  answer="The distributed lock stops two requests from touching the same seat at the same instant, but it says nothing about what 'touching' means — a class with a bare status field and scattered if/else checks can still transition a seat incorrectly even under the lock (e.g. confirming a seat that was never held). The schema/class design is what makes each individual transition correct; the lock is what makes concurrent transitions safe."
/>

## Requirements at the object level

The [HLD lesson's functional requirements](/case-studies/ticketmaster/hld)
translate into five lifecycle-bearing entities:

<Point icon="layers">
  **Search/browse events** → `Event`, `Venue`, `Show` need to be queryable
  independently of booking state.
</Point>
<Point icon="cache">
  **View live seat availability** → `Seat` needs a status that's cheap to
  read at ~100k requests/sec.
</Point>
<Point icon="clock">
  **Reserve a seat temporarily** → `Seat` needs a `LOCKED` state with an
  expiry, and something has to own "who is holding this and until when."
</Point>
<Point icon="shield">
  **Complete payment and confirm** → `Booking` needs its own lifecycle,
  separate from `Seat`'s, because one booking touches multiple seats and a
  payment can fail after seats are held.
</Point>
<Point icon="branch">
  **Cancel/expire and release** → both `Seat` and `Booking` need a path
  back to their starting state, not just a forward happy path.
</Point>

That last point is the one classes-as-status-flags usually get wrong:
release-on-expiry and release-on-cancellation are two different trigger
events that both need to land on the same `AVAILABLE` state. Implemented
as two separate ad-hoc code paths instead of one state transition, it's
easy for one of them to leak a seat that's stuck `LOCKED` forever.

## Class design

Eleven classes cover the domain: `Venue` and `SeatMap` describe the
physical space, `Event` and `Show` describe what's playing and when,
`Seat` and `PricingTier` describe an individual seat's identity and
price, `SeatInventory` describe per-show availability, and `User`,
`Booking`, `BookingItem`, and `Payment` describe who bought what. The
class diagram is split into two, by concern, rather than one diagram
carrying all eleven classes: catalog/physical classes (what a buyer
browses before committing to anything) and booking/transaction classes
(what changes once a buyer starts a hold).

*`Seat` and `Show` here are the same classes from the diagram above,
repeated only as the attachment points for `SeatInventory` — this is the
concurrency-critical half of the domain: `SeatInventory` holds the
lockable state, `Booking` is the transaction boundary, `Payment` is the
external integration point.*

The relationship worth calling out: `Seat` belongs to `SeatMap` (the
venue's fixed layout), but seat *availability* is scoped to a `Show`, not
to the `Seat` itself — the same physical seat is available for Tuesday's
show and sold out for Saturday's. That's why `SeatInventory` exists as
its own class rather than a status field on `Seat`: one row per
`(show, seat)` pair, not one row per seat. `SeatInventory` is the entity
every concurrency mechanism in this lesson attaches to: it's what holds
the `state`, the `version` (used for optimistic locking, covered under
Database design), and the `holdId` / `holdExpiresAt` pair. `Seat` itself
stays a dumb, immutable-ish description of a physical location — row,
number, tier — because that data doesn't change per show.

<QuizItem
  question="Why is seat availability modeled as a separate SeatInventory row per (show, seat), instead of a status field directly on Seat?"
  answer="A Seat is a fixed physical location that exists once per venue, but its booking status is scoped to a specific show — the same seat is available for one show and sold out for another happening the same week. Putting status on Seat would force one seat to have only one status across every show it's ever used for, which is wrong the moment a venue hosts two events."

## State machines

### Seat lifecycle

Every `SeatInventory` row moves through three states, and — this is the
part a naive `if/else` implementation gets wrong — there are two distinct
paths back to `AVAILABLE`, not one: a hold that times out, and a hold or
booking that's explicitly cancelled. A state machine forces both paths to
be named and handled instead of one being an afterthought.

<D2Diagram
  title="Seat inventory state machine"
  type="state"
  chart={`
direction: right
AVAILABLE -> LOCKED: "hold(userId) — TTL starts"
LOCKED -> BOOKED: "payment confirmed"
LOCKED -> AVAILABLE: "TTL expires"
LOCKED -> AVAILABLE: "user cancels hold"
BOOKED -> AVAILABLE: "booking cancelled / refunded"
`}
/>

*Every seat's booking state for a given show is one of three values;
the two arrows back into `AVAILABLE` from `LOCKED` are what a Redis TTL
expiry and an explicit cancel button each trigger — both have to land on
the same state or a cancelled hold and a timed-out hold would behave
differently, which they shouldn't.*

### Booking lifecycle

A `Booking` is a separate state machine from `Seat`, because a booking
can span multiple seats and its failure modes are about payment, not
about any individual seat.

<D2Diagram
  title="Booking state machine"
  type="state"
  chart={`
direction: right
PENDING -> CONFIRMED: "payment succeeds"
PENDING -> EXPIRED: "hold TTL elapses before payment"
PENDING -> CANCELLED: "user cancels before paying"
CONFIRMED -> CANCELLED: "refund issued"
`}
/>

*A `Booking` reaching `EXPIRED` or `CANCELLED` is the trigger that fires
`SeatInventory.release()` on every seat it holds — the two state
machines are coupled at exactly one point (the booking's terminal
failure states release the seats), not duplicated into each other.*

<QuizItem
  question="A user's payment fails after their 10-minute hold TTL has already expired. What state is the Booking in, and what state is the Seat in?"
  answer="The Booking is EXPIRED (the TTL elapsed before payment completed) and the Seat is back to AVAILABLE — the TTL expiry already released it via the LOCKED → AVAILABLE transition, independent of whether the payment attempt ever happens. The payment failure doesn't need its own seat-release logic because the seat was never going to still be held once the TTL passed."
/>

## Design patterns

{/* concept-dependency: LLD-03 not yet built, explained inline */}
Four patterns replace what would otherwise be scattered `if/else` blocks
checking string or enum status fields. Each is a standard "gang of four"
object-oriented design pattern — a named, reusable solution to a
recurring design problem — used here for a specific reason tied to this
domain, not because using patterns is inherently good.

### State — for Seat and Booking lifecycles

Instead of `Booking.confirm()` opening with `if (this.state !==
"PENDING") throw ...`, repeated in every method, the **State pattern**
gives each lifecycle state its own class implementing a shared interface
(`SeatState` with `hold()`, `release()`, `confirm()`), and the
`SeatInventory` object delegates to whichever state object it currently
holds. Calling `confirm()` on an `AvailableState` object simply isn't a
transition that state's implementation supports — the illegal
transition is a missing method call, not a runtime check that a future
edit might delete.

<D2Diagram
  title="State pattern — SeatState hierarchy"
  type="class"
  chart={`
SeatState: "SeatState «interface»" {
  shape: class
  +hold(userId: UUID): bool
  +release(): void
  +confirm(): void
}
AvailableState: {
  shape: class
  +hold(userId: UUID): bool
}
LockedState: {
  shape: class
  +release(): void
  +confirm(): void
}
BookedState: {
  shape: class
}
SeatInventory: {
  shape: class
  -currentState: SeatState
  +hold(userId: UUID): bool
  +release(): void
  +confirm(): void
}
AvailableState -> SeatState: implements {style.stroke-dash: 4}
LockedState -> SeatState: implements {style.stroke-dash: 4}
BookedState -> SeatState: implements {style.stroke-dash: 4}
SeatInventory -> SeatState: "delegates to current state"
`}
/>

*Each state class only implements the transitions that state actually
supports — `AvailableState` has no `confirm()` at all, so calling it
there isn't a bug caught by a check, it's a method that doesn't exist.*

{/* concept-dependency: LLD-03 not yet built, explained inline */}
This is also a concrete instance of the **Open/Closed Principle** (one
of the five SOLID principles: a class should be open for extension but
closed for modification) — adding a fourth seat state later (say,
`ON_HOLD_FOR_RESALE`) means adding one new class, not editing every
existing `if/else` chain that enumerates states.

### Strategy — for pricing

VIP, general-admission, and dynamic (demand-based) pricing are three
different algorithms for the same question: "what does this seat cost?"
The **Strategy pattern** puts each algorithm behind a shared
`PricingStrategy` interface (`calculatePrice(seat, show): decimal`) and
lets `PricingTier` hold a reference to whichever strategy applies,
instead of `BookingItem.getPrice()` branching on a tier-name string.

*Adding a fourth pricing model — say, a bundle discount — means writing
one new class that implements `PricingStrategy`; `Booking` and
`BookingItem` never change, because they only ever call
`strategy.calculatePrice(...)` through the interface.*

### Observer — for hold-release notifications

When a `SeatInventory` transitions `LOCKED → AVAILABLE` (whether by
expiry or cancellation), zero or more users who wishlisted or previously
tried to hold that exact seat need a notification. Rather than
`SeatInventory.release()` hard-coding a call to the notification
service, `SeatInventory` holds a list of `Observer` subscribers and calls
`notify(seatId)` on all of them at the moment of release. How that
dispatch actually happens is a second decision, not automatically solved
by picking Observer:

<CompareTable
  title="Observer dispatch mechanism"
  rows={[
    {
      approach: "In-process observer list",
      pros: [
        "Simple: SeatInventory.release() loops its subscriber list and calls notify()",
        "No extra infrastructure",
      ],
      cons: [
        "Lost if the SeatInventory-owning process crashes mid-dispatch",
        "Doesn't scale past one process — a second instance has its own, disconnected subscriber list",
      ],
      chosenBecause: "fine at the scale of one instance handling one seat's release",
    },
    {
      approach: "Queue/pub-sub dispatch",
      pros: [
        "Survives a process crash — the release event is durable until a subscriber consumes it",
        "Scales past one instance: any consumer group can subscribe",
      ],
      cons: ["More moving parts: a queue/topic and consumer infrastructure"],
      chosenBecause:
        "needed once notification fan-out must survive process crashes or run across multiple SeatInventory-owning instances (the HLD lesson's message queue is exactly this)",
    },
  ]}
/>

The notification service subscribes as one observer regardless of which
dispatch mechanism backs it; a future "waitlist" feature could subscribe
as a second, without touching `SeatInventory.release()` again — that
part of the Observer contract doesn't change between the two dispatch
options above.

<QuizItem
  question="A new requirement arrives: add a 'loyalty member' pricing tier that gives 15% off the base price. Which class do you touch, and which do you not touch?"
  answer="Add a new class implementing PricingStrategy (e.g. LoyaltyPricingStrategy) and register it on the relevant PricingTier — you don't touch Booking, BookingItem, or any existing pricing strategy class. That's the Strategy pattern's Open/Closed win: new pricing behavior is a new class, not an edit to existing branching logic."

## Database design

{/* concept-dependency: LLD-05 not yet built, explained inline */}
The schema splits across two storage systems on purpose, following the
HLD's Redis-for-holds decision down to the object level: relational
tables for anything that needs a transaction (bookings, payments,
confirmed seat state), and Redis — deliberately *not* a table in this
schema — for the seat hold's TTL. The relational tables themselves split
by the same catalog/booking concern boundary as the class diagrams
above.

### Normalization decisions

<Point icon="database">
  `SEAT_INVENTORY` is its own table keyed on `(show_id, seat_id)` rather
  than folded into `EVENT`/`SHOW` as a JSON blob or a denormalized
  seat-count column — individual seat rows need row-level locking and
  independent updates.
</Point>
<Point icon="lock">
  A `SHOW.available_seats_json` blob would force every hold to
  read-modify-write the entire show's seat map, serializing all
  concurrent holds on a show through one row.
</Point>
<Point icon="layers">
  One row per seat per show is the classic case for full normalization:
  each row changes independently and needs its own transaction boundary.
</Point>
<Point icon="cache">
  The one place denormalization pays off is the read path: a
  **read-optimized cache table** (or Redis hash) holding just `seat_id →
  state` per show, refreshed on every write and served for GET requests,
  avoids hitting the normalized table (with its `version` column and
  foreign keys) for every seat-map render.
</Point>

<KeyStat
  value="~100k reads/sec"
  label="seat-map render traffic against a few thousand identical rows per show"
  detail="Per the HLD lesson's capacity estimate: showing a seat-map UI for a popular show is read-dominated at roughly a 100:1 read:write ratio. A per-show read cache serves this in one lookup instead of a filtered scan of the normalized table on every request."
/>

That's denormalization for read scaling, layered on top of a normalized
source of truth — not a replacement for it.

### Indexing strategy

<Point icon="database">
  The dominant query is "show seat availability for show X":
  `SELECT seat_id, state FROM seat_inventory WHERE show_id = ?`. A
  composite index on `(show_id, state)` serves that directly and also
  serves the narrower "show only available seats for show X" query
  (`WHERE show_id = ? AND state = 'AVAILABLE'`) without a table scan.
</Point>
<Point icon="lock">
  The primary key `(show_id, seat_id)` already gives point lookups ("is
  this exact seat available") for free — no separate index needed.
</Point>
<Point icon="users">
  A second, unrelated query needs its own index: "show a user their
  booking history" (`SELECT * FROM booking WHERE user_id = ? ORDER BY
  created_at DESC`) is a different table with a different access
  pattern, so it needs its own `(user_id, created_at)` composite index
  on `BOOKING` — reusing the seat-inventory index isn't an option, they
  don't share a table.
</Point>

### SQL vs NoSQL at the object level

<Point icon="shield">
  `Booking`, `BookingItem`, `Payment`, and `SeatInventory`'s committed
  state live in a relational database because confirming a booking is a
  multi-row transaction — inserting the booking, inserting each booking
  item, and flipping each seat's state to `BOOKED` all have to commit
  together or not at all.
</Point>
<Point icon="clock">
  The seat *hold*, by contrast, is deliberately **not** a row in this
  schema: it lives in Redis as a key like `hold:SHOW_ID:SEAT_ID` with a
  TTL, set via `SET key value NX EX 600` (set-if-not-exists, 600-second
  expiry).
</Point>
<Point icon="lock">
  Redis is chosen there over a relational `hold_expires_at` column plus a
  polling cron job because TTL expiry is a first-class Redis feature —
  the lock disappears on its own the instant it expires, with no
  background sweeper needed to notice.
</Point>

The trade-off — and why the DB still carries a `state` and `version`
column too, not just Redis — is covered next.

### Concurrency at the schema level: the version column

`SEAT_INVENTORY.version` is an integer that increments on every
successful update. A hold attempt reads the current row (`state =
AVAILABLE`, `version = 4`), then issues:

```sql
UPDATE seat_inventory
SET state = 'LOCKED', hold_owner_user_id = ?, version = version + 1
WHERE show_id = ? AND seat_id = ? AND state = 'AVAILABLE' AND version = 4;
```

If a second request already locked the seat between the read and this
write, `version` is no longer `4`, zero rows match the `WHERE` clause,
the update affects 0 rows, and the application code treats that as "seat
no longer available" rather than trusting its own stale in-memory read.
This is **optimistic locking**, chosen over **pessimistic locking**
(`SELECT ... FOR UPDATE`, which holds a row lock for the duration of the
transaction) because contention on any single seat is brief — a lock
held only for the milliseconds of one `UPDATE` statement, not for the
seconds a client spends deciding whether to buy. Optimistic locking here
is defense-in-depth on top of the Redis hold from the HLD lesson: Redis
stops most collisions before they reach the database at all, and the
version check catches the residual race where two requests both pass the
Redis check in the same tick (Redis operations aren't instantaneous
across a cluster) and both reach the database's `UPDATE`.

<QuizItem
  question="Why does the version-check UPDATE include state = 'AVAILABLE' in its WHERE clause, not just version = 4?"
  answer="Belt and suspenders against two different failure modes: version alone catches any concurrent write, but including state = 'AVAILABLE' makes the guard's intent explicit and self-documenting in the SQL — a reviewer can see exactly what precondition is being enforced without having to know that version 4 currently implies AVAILABLE elsewhere in the code."
/>

## Trade-offs

<CompareTable
  title="State pattern vs. enum + if/else"

      ],
      cons: [

      ],
    },
    {
      approach: "State pattern",
      pros: [
        "Illegal transition is a missing method, not a runtime check a future edit can delete",
        "New state = one new class (Open/Closed Principle)",
      ],
      cons: ["More boilerplate: one class per state"],
      chosenBecause:
        "the domain is explicitly expected to grow (the interview angle below adds group holds, which needs at least one more state) and cross-cutting transition rules (e.g. 'no state can transition directly to BOOKED except from LOCKED') need one enforcement point",
    },
  ]}
/>

For a two-state toggle that will never change, the enum stays simpler
and the State pattern would be over-engineering — the right call depends
on whether the domain is expected to grow.

## Worked example: reserve-seat flow with a version-check retry

Two users, Priya and Marcus, both click "Select seat" on seat `C12` for
the same show within the same 50ms window. `C12`'s current
`SeatInventory` row: `state = AVAILABLE`, `version = 7`.

<D2Diagram
  title="Reserve-seat flow — concurrent hold attempt with version-check retry"
  type="sequence"
  chart={`
shape: sequence_diagram
Priya
Marcus
API: Booking Service
Redis
DB: "seat_inventory (SQL)"

Priya -> API: "POST /hold seat=C12"
Marcus -> API: "POST /hold seat=C12"
API -> Redis: "SET hold:show1:C12 priya NX EX 600"
Redis -> API: "OK (lock acquired)"
API -> Redis: "SET hold:show1:C12 marcus NX EX 600"
Redis -> API: "nil (key exists — lock held)"
API -> Marcus: "409 seat unavailable"
API -> DB: "UPDATE seat_inventory SET state=LOCKED, version=8 WHERE seat=C12 AND version=7 AND state=AVAILABLE"
DB -> API: "1 row updated"
API -> Priya: "200 held, expires in 10:00"
`}
/>

*Version now 8 after Priya's update commits — a second `UPDATE` still
carrying `version = 7` would match 0 rows.*

Marcus never reaches the database at all — the Redis `NX` (set-if-not-
exists) check rejects him at the first line of defense, which is the
point of putting Redis in front of the relational write: it turns the
common case of two people wanting the same popular seat into a cheap
in-memory rejection instead of a database round-trip. The version check
only fires for the rarer case where two requests both pass Redis in the
same instant (possible under Redis Cluster's eventual propagation across
nodes) — in that case, whichever `UPDATE` runs second matches zero rows
on the stale `version = 7` predicate, and the booking service treats a
zero-row update exactly like a Redis rejection: return 409, don't retry
against the same seat.

<QuizItem
  question="If Marcus's UPDATE happened to run first (a Redis Cluster propagation delay let both requests pass the NX check), what does his UPDATE's row count tell the application?"
  answer="1 row updated — his UPDATE matched version=7 and state=AVAILABLE, so it succeeds and bumps version to 8. Priya's subsequent UPDATE, still using the version=7 it originally read, now matches 0 rows and her request is rejected instead — the version check doesn't care about arrival order, only about which write reaches the database first with a still-valid version."
/>

## Interview angle

<Point icon="branch">
  **"Walk me through your classes."** Start from the entity a buyer
  touches first — `Event` and `Show` for browsing — then narrow to
  `SeatInventory` as the concurrency-critical entity, then `Booking` and
  `BookingItem` as the transaction boundary, then `Payment` as an
  external integration point. Naming the ownership relationships (`Show`
  owns many `SeatInventory` rows; `Booking` owns many `BookingItem`s) in
  that order shows you're reasoning about the domain, not reciting a
  class list.
</Point>
<Point icon="lock">
  **"How does this prevent double-booking at the code level?"** Two
  independent guards, not one: Redis's `SET NX` gives a fast, mostly-
  sufficient exclusion at hold time, and the `version` column's
  optimistic check on the `UPDATE` gives a correctness guarantee that
  doesn't depend on Redis being perfectly consistent. Say explicitly that
  either guard alone would be defensible, but running both is deliberate
  defense-in-depth given the stakes of overselling a seat.
</Point>
<Point icon="branch">
  **"Add a new pricing strategy without touching Booking."** A direct
  test of the Strategy pattern's payoff from earlier in this lesson:
  write a new class implementing `PricingStrategy`, wire it onto the
  relevant `PricingTier`, and `Booking`/`BookingItem` — which only ever
  call `strategy.calculatePrice(...)` through the interface — need zero
  changes. If your design requires touching `Booking` to add a pricing
  rule, that's the signal the pricing logic leaked out of its own
  abstraction.
</Point>

## Practice & Self-Check

### Recap quiz

<QuizItem
  question="Why does SeatInventory exist as a separate entity from Seat, keyed on (show_id, seat_id) rather than seat_id alone?"
  answer="Because booking status is scoped to a show, not to the physical seat — the same seat is available for one show and booked for another. Keying on seat_id alone would let one seat have only a single status across every show it's ever used in."
/>

<QuizItem
  question="Name the two distinct trigger events that both transition a seat from LOCKED back to AVAILABLE."
  answer="TTL expiry (the hold times out because the buyer didn't complete payment) and explicit cancellation (the buyer or system cancels the hold before it expires) — both have to land on the same AVAILABLE state so a timed-out hold and a cancelled hold behave identically to anyone else viewing the seat."
/>

<QuizItem
  question="Which design pattern would you reach for if a seat could switch between VIP, general, and a future 'resale' pricing tier, and why not just branch on a tier string?"
  answer="Strategy — each pricing tier's calculation becomes its own class implementing a shared PricingStrategy interface, so adding a resale tier means adding one new class instead of editing an if/else chain everywhere price is computed, which is the Open/Closed Principle in practice."
/>

<QuizItem
  question="What does the version column in seat_inventory protect against that the Redis hold alone does not?"
  answer="The rare case where two concurrent requests both pass the Redis SET NX check before either lock is visible cluster-wide — the version-checked UPDATE is a second, database-level guard that doesn't depend on Redis's consistency guarantees, so even that residual race can't double-book a seat."
/>

<QuizItem
  question="Why is the seat hold kept in Redis instead of as a status + hold_expires_at column checked by a cron job?"
  answer="Redis TTL expiry is automatic — the key disappears the instant it expires with no polling needed — whereas a DB column plus cron job means seats can stay incorrectly LOCKED for up to one cron interval after they should have released, and it adds an extra moving part (the cron job itself) that can fail silently."
/>

<QuizItem
  question="A show sells out its 5,000 seats in the first 90 seconds of an on-sale. Which table design choice from this lesson keeps the seat-map page fast under that read load, and what's the cost of that choice?"
  answer="The denormalized read cache (a per-show seat-state blob or Redis hash) in front of the normalized seat_inventory table — it serves the ~100k reads/sec in one lookup instead of a filtered table scan per request. The cost is that the cache can briefly lag the transactional source of truth, so a buyer might glimpse a seat as available for a few hundred milliseconds after it was actually locked."
/>

<QuizItem
  question="Why does Booking have its own state machine (PENDING/CONFIRMED/EXPIRED/CANCELLED) separate from Seat's (AVAILABLE/LOCKED/BOOKED), instead of deriving the booking's status from its seats' statuses?"
  answer="A single booking can span multiple seats and its failure modes are about the payment step, not any individual seat — deriving Booking's state from its seats would break the moment a booking holds two seats that could, in theory, diverge (e.g. one released by an admin override). Keeping them separate, coupled only at the point where a terminal Booking state releases its seats, keeps each state machine's job singular."
/>

<QuizItem
  question="A buyer wants to see their past bookings. Which index from the Database design section serves that query, and why can't the (show_id, state) index on SEAT_INVENTORY serve it instead?"
  answer="A (user_id, created_at) composite index on BOOKING. The (show_id, state) index lives on a different table (SEAT_INVENTORY) with a different access pattern — it's built for 'show me seat availability for a show,' not 'show me a user's bookings across every show they've bought from,' so it can't be reused across tables."
/>

### Open design challenge

Extend this design to support **group bookings of adjacent seats** — a
buyer selects 4 seats in the same row and wants an atomic guarantee:
either all 4 hold successfully, or none do (no buyer should end up with
2 of the 4 seats they wanted while the other 2 went to someone else
mid-selection).

<details>
<summary>Reference answer (try the design yourself first)</summary>

Add a `GroupHold` aggregate that wraps a list of `SeatInventory`
references and enforces all-or-nothing acquisition. Its `acquire()`
method attempts the Redis `SET NX` for every seat in the group in a
fixed order (e.g. sorted by `seat_id`, to prevent two group holds from
deadlocking each other by locking the same two seats in opposite order);
if any single `SET NX` fails, it immediately releases every lock it
already acquired in this attempt (compensating rollback, the same
pattern the HLD lesson's booking→payment saga uses at the service
level) and returns a single failure to the caller — the buyer sees "seat
C14 was just taken, please reselect" rather than partial success.

At the database layer, the version-check `UPDATE` for all N seats runs
inside one transaction with all N `WHERE version = ? AND state =
AVAILABLE` predicates; if any one seat's row doesn't match, the whole
transaction rolls back via the database's native atomicity — no seat in
the group is left `LOCKED` while its siblings failed. `Booking` already
supports this without a schema change: `BookingItem` is already
one-row-per-seat under one `Booking`, so a group booking is simply a
`Booking` with 4 `BookingItem`s instead of 1 — the class design doesn't
need a new entity there, only the new `GroupHold` coordinator for the
acquisition step.

The `SeatInventory` state machine itself doesn't need a new state —
each seat still only ever occupies `AVAILABLE`/`LOCKED`/`BOOKED`. What's
new is that `GroupHold` is the only caller allowed to invoke `hold()`
across more than one seat atomically; an individual `hold()` call
by itself still only locks its own seat.

</details>
