title: "Chat/WhatsApp: High-Level Design"

Every case study so far has been a request/response problem wearing
different clothes: a client asks, a server answers, the connection closes.
Chat breaks that shape entirely. A message has to reach a specific human
being who might be on a subway with no signal, asleep with the app closed,
or typing back within 100ms — and the server has to know which one of
those is true, for hundreds of millions of people, at every instant.

## Problem framing

Two coupled problems define this system, and neither is solvable by just
adding more servers to a stateless fleet the way search or checkout
traffic would be.

<Point icon="layers">
  **Holding the connection.** Tens of millions of clients need a
  long-lived, low-latency, bidirectional channel open to the server at
  the same time — not a request that finishes in 200ms, but a socket that
  stays alive for hours. The server has to remember, for every one of
  those users, exactly which physical machine their live connection is
  sitting on right now.
</Point>

<Point icon="shield">
  **Guaranteeing the message.** Once a message is sent, it has to arrive
  at its recipient exactly the way the sender intended: not lost, not
  duplicated, and never shown out of order relative to the rest of that
  conversation — even if the recipient's phone was off when it was sent
  and only reconnects an hour later.
</Point>

That second problem is why this is fundamentally a **stateful-connection**
system, unlike the mostly-stateless services covered in earlier case
studies. A stateless API server can hand off any request to any instance
behind a load balancer because no instance remembers anything about the
caller between requests. A chat server can't do that: if Bob's phone has
a live WebSocket open to gateway server #47, a message for Bob is useless
sent to gateway server #12 — #12 has no socket to Bob at all. The system
has to track *which server holds which user's connection* as a first-class
piece of state, and keep that mapping correct as users disconnect,
reconnect, and roam across gateway servers all day.

{/* concept-dependency: HLD-01 not yet built, explained inline */}
That state also forces an explicit choice about staleness. A user's
online/offline status is allowed to lag reality by a few seconds — nobody
is harmed if "last seen 2 minutes ago" is actually 90 seconds out of date.
A message's delivery guarantee is not allowed to lag or drop at all. So,
much like the read/write split in earlier case studies, this system leans
toward availability (serve a slightly stale presence status rather than
block) for presence, and toward durability (never silently lose a
message) for the message path itself — two different consistency
postures inside the same product, covered in their own deep dives below.

## Requirements & capacity estimate

**Functional requirements:**

- 1:1 messaging between two users, delivered in real time when both are
  online
- Group messaging (up to a few hundred members) with the same real-time
  delivery when members are online
- Delivery/read receipts — sent → delivered → read — tracked per
  recipient in a group, not just per message
- Online presence / last-seen for a user's contacts
- Persisted message history per conversation, with scroll-back pagination
- Multi-device sync — a message sent or received on one device shows up
  in the same conversation state on a linked device
- Offline delivery: a message sent to an offline user is queued and
  delivered (plus a push notification) when they reconnect

**Non-functional requirements:**

- Online-to-online delivery latency of roughly 100–300ms
- Per-conversation ordering — never out of order within one conversation,
  even under retries or jitter; no global ordering across conversations
  required
- At-least-once delivery — a message is never silently dropped; the
  client dedupes on a client-generated message ID if it arrives twice
- Massive connection scale — hundreds of millions of daily active users,
  tens of millions of concurrent persistent connections
- A single chat server or data-center failure forces a reconnect, never a
  permanently dropped account
- Durability — once a message is acknowledged "sent," it survives a
  server crash on the delivery path

**Out of scope for this lesson:** the end-to-end encryption cryptography
itself (key exchange, ratcheting) — only where encryption conceptually
sits in the flow is covered; voice/video calling; the media upload/CDN
pipeline in detail; Stories/Status; spam and abuse-rate-limiting policy.

Every client holds one persistent connection to a gateway server, which
is the only tier that ever touches a live socket. Everything the gateway
needs to route a message — which user is on which gateway, who's
currently online — lives in Redis, not in the gateway's own memory, which
matters for the failover trade-off covered later. The message service is
the single place that persists a message durably before anything else
happens to it; delivery to a live connection and delivery via push
notification are two different outcomes of the same enqueue step, not two
different code paths bolted on separately.

{/* concept-dependency: HLD-03 not yet built, explained inline */}
The "Connection Gateway" box is a fleet of ~700–1,000 machines (per the
capacity estimate above) sitting behind an L4 (transport-layer) load
balancer. Unlike the L7, path-aware routing a stateless API gateway would
use, this load balancer only needs to pick *some* healthy gateway
instance to accept a new incoming connection — it has no idea, and
doesn't need to know, which user ends up on which machine. That mapping
is decided after the connection lands, during authentication, and lives
in the session store instead.

## Deep dives

### Connection management

A persistent, low-latency, bidirectional channel is the one requirement
this whole design exists to satisfy, so the transport choice and how the
gateway tier tracks who's connected both deserve their own treatment.

- **WebSocket over polling.** Short-polling (client asks "anything new?"
  every few seconds) trades latency for simplicity — a message can sit
  waiting up to a full poll interval before the client even asks for it,
  which blows past the ~100–300ms target. Long-polling (server holds the
  request open until there's something to send) narrows that gap but
  still pays a full HTTP request/response cycle's overhead per message
  and needs a new connection re-opened after every response. A WebSocket
  upgrades one HTTP connection into a full-duplex socket that stays open
  indefinitely — the server pushes the instant it has something, with no
  request to re-issue.
- **The gateway is stateless-per-request; the routing table is the real
  state.** The gateway process itself doesn't need to remember anything
  about a user across restarts — it's the `user_id -> gateway_id` mapping,
  typically kept in Redis, that has to survive a gateway's death. Losing a
  gateway process loses its live sockets (those users get disconnected)
  but never loses the *record* of who was talking to whom, which the next
  reconnect rebuilds from durable storage rather than from a dead
  process's memory.
- **Heartbeats detect dead connections faster than TCP alone.** TCP's own
  keepalive/timeout can take minutes to notice a connection is dead (a
  phone that lost signal without a clean disconnect leaves a socket that
  looks alive to the OS for a long time). A lightweight ping/pong sent
  over the WebSocket every ~15–30 seconds, with the server expecting a
  pong back within a short window, gives a bounded, fast signal: no pong
  in time means the connection is presumed dead, its routing entry is
  cleared, and any further messages route through the offline path
  instead of a socket that will never deliver them.

### Message delivery guarantee

This is the part of the design an interviewer is really probing when
they ask "how does chat work" — three separate guarantees, each solved by
a different mechanism.

- **At-least-once delivery via persist-before-ack.** The message service
  writes a message to durable storage *before* acknowledging the sender,
  as shown in the architecture diagram above. If the service crashes
  between persisting and acknowledging, the client simply doesn't see a
  "sent" confirmation and retries — the retry is safe because the next
  guarantee (client-generated IDs) makes a duplicate write harmless rather
  than a duplicate message.
- **Client-side dedup via idempotency key.** Every message the client
  sends carries a `client_msg_id` it generated locally (e.g. a UUID) before
  the network call. If a retry causes the same message to reach the
  server twice, the message service treats a repeated `client_msg_id` for
  the same conversation as a no-op — return the existing message's
  status rather than creating a second row. This is what makes
  at-least-once delivery survivable: the network can duplicate a request
  as many times as it wants, and the visible result is still exactly one
  message.
- **Per-conversation ordering via a sequence number, not a timestamp.**
  Each conversation (a 1:1 pair or a group) has its own monotonically
  increasing counter. Every message persisted into that conversation gets
  the next number — `conv_118_seq_42`, then `43`, then `44` — and clients
  render messages sorted by that number, not by wall-clock timestamp.
  Wall-clock timestamps from different senders' devices can't be trusted
  to agree closely enough (clock skew, network jitter) to guarantee two
  near-simultaneous messages render in the order they were actually
  accepted by the server; a single counter owned by the message service
  for that one conversation has no such race, because it only has to be
  consistent with itself, not with every other conversation in the
  system.
- **Read receipts are a separate status pipeline, not a message-row
  field.** Sent/delivered/read status is tracked per `(message, recipient)`
  pair, not baked into the message itself — a group message has one row
  in the message store but N independent receipt entries, one per
  recipient, each moving through its own sent → delivered → read
  transitions on its own schedule. Modeling status as a separate,
  append-only stream keeps the (much larger) message store itself
  write-once, and lets receipt updates — which are far more frequent than
  new messages, since read status keeps changing — scale independently.

### Online presence / last-seen

Presence looks like a small feature but is a fan-out problem in its own
right, and it's the one place in this design that deliberately tolerates
staleness.

- **Heartbeat-driven, TTL-based presence.** The system overview diagram's
  gateway → presence edge is the mechanism: connecting (or each
  heartbeat) refreshes a Redis key like `presence:user_42 = online` with
  a short TTL, e.g. 30 seconds. If heartbeats stop — the app is
  backgrounded, the connection drops — the key simply expires on its own
  a few seconds later and the user reads as offline, with no explicit
  "going offline" message required from a client that may not get the
  chance to send one.
- **Presence fan-out is the actual scale problem, not the read.** A single
  presence lookup is cheap. The expensive part is that hundreds of
  contacts might care about one user's status changing, and none of them
  should have to poll for it. WhatsApp's approach is to narrow this
  aggressively: presence is only pushed to a user's *mutual* contacts, and
  in practice only to the ones with an open conversation view on screen
  right now — not broadcast to an entire contact list on every connect
  and disconnect.
- **Presence tolerates a few seconds of staleness on purpose.** Unlike
  message delivery, where a dropped or duplicated update is a correctness
  bug, a presence update lagging real status by a couple of seconds is
  invisible to a user — "online" flipping to "last seen a few seconds
  ago" a beat late costs nothing. That gives the system room to batch or
  debounce presence-change fan-out rather than pushing every flicker
  instantly, trading a little freshness for a lot less fan-out traffic.

<QuizItem
  question="A user's app crashes without sending any 'going offline' signal. How does the system still show them as offline within seconds?"
  answer="Presence is TTL-based, not event-based: the presence key only stays 'online' because heartbeats keep refreshing its TTL. Once heartbeats stop (the crash means none get sent), the key expires on its own after the TTL window (e.g. 30 seconds) — no explicit offline signal from the client is required."
/>

### Group-chat fan-out

A group message has to reach every member, not one recipient — which
turns a single write into up to a few hundred, and where those writes
happen is a real design decision, not a detail.

- **Fan-out-on-write.** The message service pushes a copy to every
  member's delivery path (live socket or offline inbox) at send time, as
  drawn above. Online members see it in ~100–300ms like a 1:1 message;
  the cost is upfront write amplification — one send becomes N writes,
  which is expensive for a 10,000-member broadcast channel.
- **Fan-out-on-read.** The message is written once, keyed by group ID;
  members pull it on their next reconnect or scroll-back rather than
  having it pushed to them individually. This avoids the write
  amplification entirely but adds latency for online members, who now
  have to poll or be separately notified rather than receiving a push.
- **Hybrid by group size.** Small-to-medium groups (the common case —
  family chats, work teams, up to a few hundred members) use fan-out-on-
  write, since the write amplification is small and the latency win for
  online members matters. Very large broadcast-style groups fall back to
  fan-out-on-read (or a hybrid: push a lightweight notification, let
  clients pull the actual content), since pushing a full copy to tens of
  thousands of members on every message would overwhelm the delivery
  queue for a case real products treat differently (broadcast lists,
  channels) from ordinary group chat.

<QuizItem
  question="A 5-person family group chat and a 50,000-member public broadcast channel both need to deliver messages to their members. Why might they use different fan-out strategies?"
  answer="Fan-out-on-write costs one write per member, which is trivial for 5 people but explodes into 50,000 writes per message for the broadcast channel — an amount of write amplification the delivery queue and offline-inbox writes can't sustain. The broadcast case is better served by fan-out-on-read (or a hybrid push-notify/pull-content split), trading a little latency for members to avoid that write storm."

### Offline delivery & push notification fallback

When the session-store lookup in the 1:1 delivery flow finds no live
gateway for a recipient, the message doesn't wait — it goes durable
immediately and a push notification does the one job it's good at:
telling a closed app to come back and check.

- **The push notification is a wake-up signal, not the transport.** The
  payload delivered by APNs/FCM is typically empty or minimal (just
  enough to trigger the OS to wake the app) — the actual message content
  never leaves the offline inbox until the client reconnects over its own
  authenticated WebSocket and explicitly syncs. Putting real message
  content inside a push payload would mean trusting the push provider
  with plaintext content and losing the durability guarantee if the push
  itself is dropped, which push delivery doesn't promise the way this
  system's own inbox does.
- **The offline inbox is a durable, per-recipient queue**, not a
  best-effort cache — the same store the message service already writes
  to at send time (per the persist-before-ack step above), just read from
  a different angle: "everything not yet delivered to recipient X,"
  bounded by a retention window (e.g. 30 days) after which an
  unreachable account's backlog is dropped.
- **Reconnect sync uses the per-conversation sequence number.** The
  client tells the server the last sequence number it has for each
  conversation; the server returns everything after that number, in
  order — the same ordering mechanism from the delivery-guarantee deep
  dive doing double duty here as a resumption cursor, rather than a
  separate "what did I miss" mechanism.

<QuizItem
  question="Why doesn't the push notification itself carry the message text, since APNs/FCM could technically deliver a short payload?"
  answer="Push delivery is best-effort and the provider is a third party the client has no durability guarantee from — if the push is dropped, content inside it is gone. Keeping the push as a content-free wake-up signal and the actual message in the durable offline inbox means a dropped push only delays delivery (the client still syncs its full backlog on its next connect), never loses a message."
/>

### Message storage

- **Write-heavy, append-mostly, partitioned by conversation.** Messages
  are essentially never updated once written (only their separate
  read-receipt status changes, per the delivery-guarantee deep dive), so
  the store is optimized for high-throughput appends rather than
  in-place updates. Partitioning by `conversation_id` keeps every message
  in one conversation physically close together, which matters directly
  for the next point.
- **Scroll-back access shapes the schema, not just the write path.**
  "Show me the last 50 messages in this conversation, then the 50 before
  that" is the dominant read pattern — a query that wants messages for
  one conversation, ordered by sequence number, in contiguous chunks. A
  wide-column store keyed by `conversation_id` with `seq` as the sort key
  (or an equivalent partition/sort-key design in a document store) serves
  that access pattern directly; a single flat `messages` table with a
  global index would force cross-partition scatter-gather for the exact
  query this system runs constantly.
- **Separate storage for hot (recent) vs. cold (old) history** is a
  natural extension once the schema above is in place: recent messages
  stay on fast storage close to the delivery path, older history can move
  to cheaper storage, since scroll-back into last year's messages is far
  rarer and can tolerate higher latency than the last 50 messages loading
  when a conversation opens.

### End-to-end encryption (conceptual placement only)

- **The server relays ciphertext it cannot read.** Encryption and
  decryption both happen on the client — the sender encrypts before the
  message ever leaves the device, and only the recipient's device can
  decrypt it. Every component in the architecture diagram above (message
  service, queue, message store) stores and moves an opaque encrypted
  blob; none of them need, or get, the plaintext.
- **This changes what "the server" can and can't do.** Search across
  message content, spam-scanning message text, or generating a link
  preview server-side are all *harder or impossible* once the server
  never sees plaintext — a real constraint this design accepts rather
  than works around, matching the non-goal in this lesson's scope.
- **The key-exchange and ratcheting protocol itself is explicitly not
  designed here** — only where the encryption boundary sits in the
  architecture (client-to-client, opaque to every server component) is in
  scope for this lesson, per this case study's stated boundaries.

Alice's client only ever sees one message go out — `conv_seq=118`,

milliseconds, while Carol's copy sits in the durable offline inbox for
an hour, survives however many server restarts happen in that hour, and
gets delivered the moment she reconnects and syncs from `seq=117`

delivery receipt — Carol's "delivered" doesn't arrive until she's back
online, and her "read" receipt (not shown) would follow only once she
actually opens the conversation, same as Bob's.

## Interview angle

**"How do you scale presence to hundreds of millions of users without a
presence-update storm on every reconnect?"** Two levers, both covered
above: narrow the fan-out (push status only to mutual contacts with that
conversation open, not a whole contact list) and accept staleness
(batch/debounce updates over a couple of seconds instead of pushing every
flicker instantly). The naive version — broadcast every connect/disconnect
to every contact immediately — is exactly what those two levers exist to
avoid.

**"What happens when a user sends a message and the network drops before
the ack?"** The client doesn't know whether the message reached the
server or not, so it can't safely assume either outcome — it has to
retry. That retry is only safe because of the at-least-once + client-ID
dedup mechanism from the delivery-guarantee deep dive: if the original
send actually succeeded server-side, the retry is recognized as a
duplicate `client_msg_id` and returns the existing message's status
instead of creating a second one, so retrying blind is always the right
move.

**"How would you support message search across a user's entire
history?"** Not covered as a full section in this lesson, but worth
naming: the message store above is optimized for conversation-ordered
scroll-back, not full-text search, so search typically needs a separate
index (e.g. a search-optimized store keyed by user, populated
asynchronously off the same write path) rather than querying the primary
message store directly — and, per the end-to-end-encryption deep dive,
server-side search over content becomes impossible once the server never
sees plaintext, which is exactly why some real chat apps only support
on-device search.

### Open design challenge

**Extend the design to support disappearing messages** — a per-conversation
setting where every message sent auto-deletes, on all of a user's
devices, N hours after it was sent (a real WhatsApp feature). Think
through: where does the "delete at" timestamp get set and by what
(sender's clock or server's clock)? What actually has to happen for a
message to be "gone" — does it need to disappear from the message store,
every device's local cache, and the offline inbox, or just some of
those? What happens to a message that was queued in the offline inbox for
a recipient who was unreachable for longer than N hours — does it still
get delivered, or does it expire before ever reaching them? And how does
a newly linked device (multi-device sync, added after the message was
sent) end up without a copy of a message that already disappeared
everywhere else?

<details>
<summary>Reference approach (click to reveal)</summary>

- **Setting the expiry**: stamp `expires_at = server_persist_time + N
  hours` using the message service's own clock at the moment it persists
  the message (the same durable-write step already in this design) —
  never the sender's device clock, for the same clock-skew reason
  `conv_seq` isn't based on client timestamps either.
- **Deleting everywhere it's stored**: the message row in the message
  store gets a TTL (or a background sweep job matching Ticketmaster-style
  reapers) tied to `expires_at`; any offline-inbox entry for that message
  gets the same TTL so it can't outlive its own expiry sitting in a
  queue; each client, on receiving the message, schedules a local delete
  at `expires_at` too, so it disappears from on-screen history without
  waiting for a server round trip at the exact expiry instant.
- **A message that expires before ever reaching an offline recipient**:
  the offline-inbox TTL from the point above means it should expire, not
  linger — if Carol reconnects after `expires_at` has already passed, the
  reconnect-sync fetch (from the offline-delivery deep dive) simply
  shouldn't return that message at all, exactly as if it had never been
  queued. This is a deliberate product choice, not an edge case to patch
  around: "disappearing" has to mean disappearing even for someone who
  was offline the whole time.
- **A newly linked device after the message already disappeared**: since
  a disappearing message is never expected to persist long-term, a
  device linked after `expires_at` simply never receives it via history
  sync — multi-device sync only replays what's still in the message
  store/offline inbox at sync time, and an expired message has already
  been removed from both, so there's nothing inconsistent to reconcile,
  only content that legitimately no longer exists anywhere.

</details>
